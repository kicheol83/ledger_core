# Database

Migrations live here rather than inside `apps/api` because the schema belongs
to the database, not to one application. The outbox worker, future services
and operational scripts all read the same schema; making it a dependency of
the API package would misrepresent that.

## Commands

```bash
pnpm migrate           # apply pending migrations to the dev database
pnpm migrate:status    # dry run — show what would be applied
pnpm migrate:down      # roll back exactly one migration
pnpm migrate:redo      # roll back one and reapply (verifies reversibility)
pnpm migrate:create X  # scaffold a new migration file
pnpm migrate:test      # apply to the test database (.env.test)
pnpm db:reset          # destroy volumes, recreate, migrate from scratch
```

## Conventions

**Plain SQL only.** Migrations are run with `-j sql`, so each file is SQL, not
a JavaScript DSL. The schema depends on deferred constraint triggers,
partitioning and `plpgsql` functions — none of which a migration generator
produces correctly. Writing the SQL directly means the file is exactly what
runs.

**Every migration is reversible.** The down section must return the schema to
its previous state, and `pnpm migrate:redo` must succeed. This is checked in
review; a migration that cannot be reversed needs an explicit comment saying
why.

**Migrations are immutable once merged.** A merged migration has run in CI and
possibly elsewhere. Changing it means environments silently diverge — the
applied-migrations table records it as done and the new content never runs.
Corrections are new migrations.

**Additive-then-destructive for column changes.** Renaming or dropping a
column in a single migration breaks any running instance of the previous code
version during a rolling deploy. Split it: add the new column and backfill in
one release, switch the code, drop the old column in a later release.

**No data mutations in schema migrations.** Backfills belong in separate,
explicitly named migrations so a schema rollback does not silently revert
business data — and so a long-running backfill can be reviewed for how long it
holds locks.

## Lock awareness

`ALTER TABLE` takes an `ACCESS EXCLUSIVE` lock. On a hot table this blocks
every read and write for the duration, and worse, it queues behind existing
transactions while newer queries queue behind it. On PostgreSQL 16 the
following are metadata-only and safe:

- `ADD COLUMN` without a volatile default
- `ADD COLUMN ... DEFAULT <constant>` (no table rewrite since PG 11)
- `DROP COLUMN` (marks invisible, space reclaimed by vacuum)

These are not, and need care on a populated table:

- `ADD COLUMN ... DEFAULT <volatile expression>` — full rewrite
- changing a column type — full rewrite
- `ADD CONSTRAINT ... CHECK` — full scan unless added `NOT VALID` first, then
  validated in a second statement
- `ADD FOREIGN KEY` — same; use `NOT VALID` then `VALIDATE CONSTRAINT`
- `CREATE INDEX` — blocks writes; use `CREATE INDEX CONCURRENTLY`, which
  cannot run inside a transaction block

Migrations run inside a transaction by default. For statements that cannot
(`CREATE INDEX CONCURRENTLY`), disable it for that file:

```sql
-- Up Migration
-- transaction: false
CREATE INDEX CONCURRENTLY idx_example ON example (column);
```

## Naming

`<timestamp>_<kebab-case-description>.sql`, generated by `pnpm migrate:create`.
The timestamp prefix determines apply order and prevents the merge-order
collisions that sequential numbering causes on parallel branches.
