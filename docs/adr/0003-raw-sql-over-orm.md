# ADR-0003: Use raw SQL instead of an ORM

- **Status:** Accepted
- **Date:** 2026-01-15

## Context

The correctness properties of this system are PostgreSQL features, not
application patterns:

- `SELECT ... FOR UPDATE` with a deterministic lock order
- `DEFERRABLE INITIALLY DEFERRED` constraint triggers that fire at `COMMIT`
- `FOR UPDATE SKIP LOCKED` for concurrent outbox workers
- explicit isolation levels per transaction
- `INSERT ... ON CONFLICT ... RETURNING` for idempotency

Whatever data access layer is chosen has to express all of these precisely,
and it has to be obvious from reading the code which SQL will actually run.

## Options considered

### Prisma

Excellent developer experience and type safety for CRUD. It does not express
row-level locking, `SKIP LOCKED`, or deferred constraint semantics, and its
interactive transaction API abstracts the connection in ways that make lock
scope hard to reason about. Reaching for `$queryRaw` for every important
operation means paying Prisma's cost while bypassing its benefit.

### TypeORM

Supports pessimistic locking and raw queries. The cost is elsewhere: query
generation is opaque enough that the emitted SQL routinely differs from what
was intended, and its migration generation produces changes that need review
anyway. For a system where the SQL _is_ the design, an unpredictable generator
is a liability.

### Kysely

A typed query builder that compiles predictably to SQL and supports locking
clauses. This is the strongest alternative — it keeps SQL semantics visible
while giving compile-time column safety.

The reason it is not chosen here is narrow: the most interesting statements in
this system are already hand-written SQL with CTEs and trigger interactions,
and a builder adds an indirection layer over exactly the code that should be
read literally. For a larger CRUD surface the trade would go the other way.

### Raw SQL through `pg`

Full access to every PostgreSQL feature. The SQL in the file is the SQL that
runs. Query plans can be reasoned about directly, and `EXPLAIN ANALYZE` output
maps one-to-one onto source.

The cost is no compile-time link between query results and TypeScript types,
and manual mapping of rows to domain objects.

## Decision

Use raw SQL via `pg`, with all queries confined to the `infrastructure` layer
of each module.

Types are handled by declaring an explicit row interface per query and running
integration tests against a real database — the tests, not the compiler, are
what guarantee the shape is right. Since every query is already covered by an
integration test for behavioural reasons, this adds no separate effort.

Parameterized queries only. String interpolation into SQL is banned and
enforced by lint rule.

## Consequences

Every PostgreSQL feature is available without escape hatches, and the transfer
path can be read as a sequence of statements in a known order — which is what
makes lock ordering reviewable.

Query plans are stable and directly attributable to source, which makes the
performance work in the load-testing phase meaningful.

The costs are real. There is no compile-time guarantee that a row interface
matches the query, so a schema change that is not reflected in a row type
fails at runtime rather than at build time. Integration tests cover this, but
the feedback is slower than a compiler error.

Boilerplate increases: mapping rows to domain objects is manual, and repeated
query fragments must be composed by hand rather than generated.

Migrations are hand-written SQL. This is partly the point — the constraint
triggers and partitioning in this schema cannot be generated by any tool — but
it means schema changes are more deliberate and slower to write.

## Revisit if

The CRUD surface grows substantially beyond the ledger core — for example an
admin or reporting module with many simple tables. Introducing Kysely for that
module alone, while keeping the ledger on raw SQL, would be a reasonable
outcome.
